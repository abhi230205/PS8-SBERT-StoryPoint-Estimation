Abstract

Agile teams give every task a story point value that shows how much effort it needs. In this project we tried to predict story points automatically from the text of a task. We used SBERT to turn each sentence of the task into a vector, and a small three-layer CNN to predict the story points from these vectors. The model is trained on one software project and tested on the most recent issues of a different project, for all 39 project pairs given in the guidelines.

On the held-out test sets the model gets a mean absolute error (MAE) of {{NUM:main:cnn.test_mae_mean_over_pairs:.2f}} and a median absolute error (MdAE) of {{NUM:main:cnn.test_mdae_mean_over_pairs:.2f}} story points. This is almost the same as a simple baseline that always predicts the median story point of the training project (MAE {{NUM:main:median_baseline.test_mae_mean_over_pairs:.2f}}, MdAE {{NUM:main:median_baseline.test_mdae_mean_over_pairs:.2f}}). The model does beat this baseline inside its own training project, so it learns something from the text. That knowledge, however, does not carry over well to a new project, mainly because every team uses its own story point scale.

1. Introduction

In agile software development, work is split into small tasks called issues (or user stories). Before the team starts working, it estimates the effort of each issue in story points, a relative number such as 1, 2, 3, 5 or 8. Good estimates help with planning, but they take time and depend on experience. Machine learning can help by predicting the story points directly from the issue's title and description. For example, from the text “Fix the login failure when a user enters an incorrect password” the model should output a number like 2.

A model is most useful for a new project that does not have much history yet. Such a project has to use a model trained on another project. Also, in real life we always predict future issues using past data. Our problem statement combines both of these ideas.

Problem statement (PS-8): Evaluate SBERT-based sentence embeddings for predicting story points of later issues in a target project using chronological ordering.

Our objectives were to:

  1. Represent each issue using SBERT sentence embeddings.
  2. Train a three-layer CNN on a source project and test it on the latest issues of a different target project, for all 39 project pairs given in the guidelines.
  3. Choose settings using five-fold validation on the training data only, and use the test data only once at the end.
  4. Report MAE and MdAE, compare with simple baselines, and discuss the results and their limitations.

2. Background

2.1 Sentence embeddings and SBERT

A computer cannot use text directly, so the text must be turned into numbers, called an embedding. Word embeddings (for example from BERT) give one vector per word. Sentence embeddings give one vector for a whole sentence. SBERT (Sentence-BERT, Reimers & Gurevych, 2019) is a BERT model trained so that sentences with a similar meaning get similar vectors. We used the pre-trained SBERT model all-mpnet-base-v2, which turns any sentence into a vector of 768 numbers.

2.2 Cross-project and chronological evaluation

  • Cross-project: the model is trained on one project (the source) and tested on another project (the target).
  • Chronological (temporal) ordering: issues are sorted by their creation date, and the test set contains the latest issues. This is more realistic than a random split, where the model could learn from issues created after the ones it is tested on.

2.3 Evaluation metrics

If y is the true story point and ŷ the prediction, then MAE = mean(|y − ŷ|) and MdAE = median(|y − ŷ|). Both are measured in story points, and lower is better. MdAE is less affected by a few very wrong predictions. We also compare against two simple baselines that do not read the text at all: always predicting the median, or the mean, story point of the training project. A useful model should beat these baselines.

3. Dataset

We used the TAWOS dataset (Tawosi et al., MSR 2022). It contains issues from the Jira trackers of 39 open-source agile projects of 12 organisations (such as Apache, Atlassian and MongoDB). It is shared as one large MySQL database file (637 MB zipped, 4.3 GB unzipped). Instead of installing MySQL, we wrote a Python script that reads the file directly and extracts only the tables we need (issues and projects). All 39 projects have story points, and they are exactly the 39 projects used in the guideline's project-pair list.

Cleaning. We removed issues that are not useful for learning effort:

  • Issues that were not completed (e.g. Won't Fix, Duplicate, still open), because their story points do not reflect real work.
  • Issues with 0 story points, or more than 100 (clear data-entry mistakes; the largest value in the raw data was 26,710,114).
  • Exact duplicates.

This left 51,777 issues out of 65,427. The projects are very different in size, from 103 issues (Java driver) to 17,894 issues (Lsstcorp Data Management). They also use different story point scales: the typical issue is worth 1 point in some projects and 5–8 points in others.

Text. For each issue we used the title plus the description. TAWOS also provides a version of the description without code snippets, which we used. We removed links and Jira formatting, and split the description into sentences. An issue has 6.8 sentences on average.

Note on project names. One name in the guideline pair list, “C++ driver (Appcelerator)”, does not exist in TAWOS. The only TAWOS project left unmatched is Aptana Studio, which belongs to the Appcelerator group of projects, so we used it for this name.

4.2 Text representation with SBERT

Every issue is turned into a list of sentences: the title first, then the description sentences in order. We keep at most 24 sentences, which covers 97% of the issues. Each sentence goes through the SBERT model, which gives a 768-number vector. So every issue becomes a 24 × 768 matrix; shorter issues are padded with zeros, and a mask tells the model which rows are real. The SBERT model itself is not trained further: we only use it to produce the vectors. Encoding all 51,777 issues took about 6 minutes on our laptop GPU (NVIDIA RTX 4080).

4.3 The three-layer CNN

A 1-D convolutional neural network (CNN) reads the matrix. Each filter looks at three neighbouring sentences at a time, so it can use information that is spread over a few consecutive sentences rather than just one.

Figure 2: Data split for one project pair (shown for the run where fold 3 is the validation fold).

  • Test set: the latest 20% of the target project's issues (an 80:20 chronological split). The model never sees these issues during training or while we choose settings. The older 80% of the target project is not used at all, so the model knows nothing about the target project.
  • Training data: all issues of the source project, sorted by date and cut into 5 folds of equal size. In five runs, four folds are used for training and one for validation, so every fold is the validation fold once.
  • Choosing the settings: we tried four settings (learning rate 0.001 or 0.0003, dropout 0.2 or 0.5) and picked the one with the lowest average validation MAE over the five folds.
  • Final model: trained on all the source data with the chosen setting, then tested once on the test set. We repeated this with three random seeds (42, 43, 44) and report the average.

5.4 Extra checks

  • Validation that always looks forward in time. In our five-fold validation, the model is sometimes trained on issues that are newer than the validation issues. To check that this did not affect our choices, we also ran a “forward-chaining” validation, where the model is always validated on newer issues. The average validation MAE was almost the same ({{NUM:main:secondary_cv_mae_mean_over_pairs:.2f}} vs {{NUM:main:cnn.val_mae_mean_over_pairs:.2f}}).
  • Training only on issues older than the test issues. We also tried using only those source issues that were created before the target's test issues. This is possible for only {{NUM:main:compare_strict.n_common_pairs:}} of the 39 pairs; for the other 10, the source project is newer than the target. The model again performed the same as the median baseline (MAE {{NUM:main:compare_strict.strict_test_mae_mean:.2f}} vs {{NUM:main:compare_strict.strict_median_baseline_mae_mean:.2f}}).

6. Discussion

6.1 Which representation achieves the lowest MAE and MdAE?

Our problem statement only covers SBERT sentence embeddings, so we compared SBERT + CNN with the two baselines.

  • Lowest MdAE: SBERT sentence embeddings + CNN ({{NUM:main:cnn.test_mdae_mean_over_pairs:.2f}}). For a typical issue, our model's error is the smallest.
  • Lowest MAE: the median baseline, by a very small and not significant margin ({{NUM:main:median_baseline.test_mae_mean_over_pairs:.2f}} vs {{NUM:main:cnn.test_mae_mean_over_pairs:.2f}}). If all 10,354 test issues are counted together instead of averaging per pair, our model has the lowest MAE ({{NUM:main:cnn.pooled_test_mae:.2f}} vs {{NUM:main:median_baseline.pooled.0:.2f}}).

We saved the exact train/test split of every pair in our repository (results/splits/). The groups working on BERT word embeddings (PS-4) and combined embeddings (PS-12) for the same setting can therefore compare with us on exactly the same test issues.

6.2 Possible explanations for the results

  1. Every team has its own story point scale. “3 points” in one project can mean the same work as “8 points” in another. The bigger the difference between the typical story point of the training and the test project, the bigger the error (correlation r = {{NUM:main:corr_abs_median_sp_shift_vs_test_mae:.2f}}). A model that only reads text cannot know the scale of a new team.
  2. The text says only a little about effort. Even inside one project, the model is only a little better than the median. When the signal is this weak, the safest prediction for MAE is close to the median. In about half of the pairs, the model learned to predict almost the same value for every issue.
  3. SBERT captures meaning, not effort. SBERT was trained to find sentences with similar meaning. Two issues can be about very similar topics but need very different amounts of work, and we did not fine-tune SBERT for effort.
  4. Projects change over time. The test issues are the newest ones. Teams change how they estimate over the years, which makes the newest issues harder to predict.

6.3 Limitations and threats to validity

  • Story points are subjective. They depend on each team, so comparing MAE between projects is not completely fair. We report results for every pair as well as the average.
  • Small search for settings. Because of limited time and compute, we tried only four settings. A larger search, or fine-tuning SBERT, might give better results.
  • Small test sets. Some test sets are very small (as few as 21 issues), so the results for those pairs are not very reliable.
  • Validation folds. In four of the five folds the model is trained on some newer issues. Our forward-chaining check (Section 5.4) showed that this did not change the results much.
  • Our choices. The cleaning rules and the mapping of “C++ driver (Appcelerator)” to Aptana Studio are our own decisions. Different choices could change the numbers a little.
  • Generalisation. We used only open-source projects with English text and one training project per test project. The results may be different for company projects, or when training on several projects together.

7. Conclusion and what we learned

We built a complete pipeline that predicts story points from issue text using SBERT sentence embeddings and a three-layer CNN, and we evaluated it on 39 cross-project pairs with chronological splits. The model reaches a test MAE of {{NUM:main:cnn.test_mae_mean_over_pairs:.2f}} and MdAE of {{NUM:main:cnn.test_mdae_mean_over_pairs:.2f}} story points. That is about the same as always predicting the training project's median, but with a slightly lower median error. The model does learn useful information from the text inside its own project. When it moves to a new project, the difference in story point scales between teams cancels out this advantage.

What we learned from this project:

  • Always compare with a simple baseline. Our model looked good on its own, but the median baseline showed that most of the work was done by predicting typical values.
  • How the data is split matters a lot. Chronological, cross-project testing is much harder (and more honest) than a random split inside one project.
  • A good validation score on one project does not guarantee good results on another project.
  • Real datasets need careful cleaning. We found story points as large as 26 million.

Future work: use a few labelled issues of the new project to adjust the story point scale; train on several source projects together; fine-tune SBERT for effort estimation; and combine sentence embeddings with BERT word embeddings.

8. How to run the code

All code, settings and results are in our GitHub repository (link on the first page). After installing the requirements (see README.md), the full experiment can be repeated with one command, and the demo predicts story points for any text:
